### 01\. 미래 모빌리티 트렌드 <sub>(2025.12.18 ~ 2025.12.22)</sub>  
> **📝 학습 내용**  
> 자동차 산업의 CASE·SDV 전환 흐름과 EV/PHEV/FCEV·UAM·하이퍼루프 등 미래 모빌리티 핵심 기술을 학습하고, 모빌리티 서비스 변화와 한국 자동차 산업 대응 전략을 바탕으로 팀 단위 아이디어 기획 및 발표를 수행  

<details>
  <summary>📚 상세 학습 내용 보기</summary>
  
---

**1. 자동차 산업의 변화**  
- [자동차의 플랫폼화] - 자동차는 단순한 이동수단을 넘어, 다양한 센서와 통신기술을 기반으로 클라우드와 연결되는 소프트웨어 중심의 지능형 주행 플랫폼으로 변화하고 있다.  
- [CASE] - 미래 자동차 산업은 차량 간·인프라 간 연결(Connected), 공유·서비스 중심 이용 구조(Shared/Service), AI 기반 자율주행(Autonomous), 전기차 중심 전동화(Electric)로 재편되고 있다.  
이러한 변화로 자동차 산업은 연결성, 자율주행, 공유·서비스화, 전동화를 중심으로 성장하고 있으며, 시장 구조 역시 그 방향으로 전환되고 있다.  

**2. 모빌리티 비즈니스의 변환**  
모빌리티 비즈니스는 차량 판매 중심의 제조 산업에서 벗어나, 자율주행·전동화·플랫폼 기반 서비스 중심 산업으로 전환되고 있다.
소유에서 이용으로 패러다임이 변화하며 로보택시, 차량 인포테인먼트, V2G 에너지 서비스 등 새로운 수익 모델이 창출되고 있다.
결국 자동차는 단순한 이동수단이 아니라, 데이터와 네트워크를 기반으로 다양한 서비스를 제공하는 모빌리티 플랫폼으로 진화하고 있다.  

**3. 패러다임 변환 주요기술**  
- [HEV 하이브리드] - 내연기관과 전기모터를 함께 사용해 연비를 향상시키고 배출가스를 줄이는 차량으로, 외부 충전 없이 주행 중 배터리를 충전한다.  
- [EV 전기차] - 배터리에 저장된 전기에너지만으로 모터를 구동하는 차량으로, 배출가스가 없고 외부 전력 충전을 통해 운행한다.  
- [PHEV 플러그인 하이브리드] - 내연기관과 전기모터를 함께 사용하지만 외부 충전이 가능하며, 일정 거리까지는 전기만으로 주행할 수 있다.  
- [FCEV 수소전기차] - 수소와 산소의 화학반응을 통해 전기를 생산해 모터를 구동하는 차량으로, 배출물은 물(H₂O)만 발생한다.  
- [UAM (Urban Air Mobility) 도심 항공 모빌리티] - 도심 내 교통 혼잡을 해결하기 위해 전기 기반 수직이착륙기(eVTOL)를 활용해 사람과 화물을 운송하는 차세대 항공 모빌리티 시스템이다.  
- [하이퍼루프 (Hyperloop)] - 진공에 가까운 튜브 내부에서 캡슐형 열차를 자기부상 및 전자기 추진 방식으로 이동시켜 초고속으로 사람과 화물을 운송하는 차세대 교통 시스템이다.  

**4. SDV와 차량용 OS**  
- [SDV (Software Defined Vehicle)] - 차량의 기능과 성능이 하드웨어가 아니라 소프트웨어에 의해 정의되고, 업데이트를 통해 지속적으로 확장·개선되는 차량이다.  
- [차량용 OS (Automotive Operating System)] - 차량 내 ECU와 애플리케이션을 제어·관리하기 위해 사용되는 운영체제로, 하드웨어와 소프트웨어 사이를 연결하는 핵심 플랫폼이다.  

**5. 모빌리티 서비스 현황과 방향성**  
모빌리티 서비스는 단순한 교통수단 제공을 넘어, ICT 기반의 스마트 기술을 활용해 이동을 통합·최적화하는 서비스 개념으로 확장되고 있다.
기존 교통체계는 혼잡, 안전·환경 문제, 비효율성 등의 한계를 가지고 있으며, 이를 해결하기 위해 공유경제 확산, 플랫폼화, 데이터 기반 운영이 강화되고 있다.
특히 자율주행 기술 발전과 함께 로보셔틀, 무인 운송 서비스 등 스마트 모빌리티가 새로운 혁신 방향으로 제시되고 있다.  

**6. 한국자동차 산업의 현황과 대응전략**  
글로벌 탄소중립과 전기차·SDV 확산에 대응하기 위해 한국 자동차 산업은 친환경차 보급 확대와 충전·수소 인프라 확충에 집중하고 있다.
배터리 안전성 강화, 공급망 안정화, 핵심 소재·차세대 배터리 기술 개발을 통해 산업 경쟁력을 높이려는 전략을 추진 중이다.
또한 자율주행과 스마트 모빌리티 기술 고도화를 통해 미래 모빌리티 시장 선점을 목표로 하고 있다.

### 05\. 자동차 소프트웨어 개발 프로세스 <sub>(2026.01.22 ~ 2026.01.28)</sub>  
> **📝 학습 내용**  
> V-Model 기반 자동차 소프트웨어 개발 생명주기와 A-SPICE의 SYS/SWE 프로세스, ISO 26262의 기능 안전 개념과 ASIL 체계를 학습하고, 요구사항 분석부터 설계·구현·통합·검증·형상관리까지 차량용 SW 개발 전 과정을 이해  

<details>
  <summary>📚 상세 학습 내용 보기</summary>
  
---

**자동차 SW 개발 프로세스**
- [자동차의 전장화와 소프트웨어 시스템의 증가] - 현재 자동차 산업은 SDV(Software Defined Vehicle)로 전환하며 소프트웨어가 차량의 전 방위적인 혁신을 일으키는 가장 중요한 요소가 되고 있음
- [글로벌 차동차 OEM 업체들의 품질 요구사항] - 프로세스 품질(Process Quality)과 제품 품질(Product Quality)의 두 가지 관점으로 구분되어 평가됨
- [소프트웨어의 정의와 특징] - 소스 코드 프로그램을 포함하여 프로세스를 통해 만들어진 모든 산출물(요구사항 명세서, 아키텍처 설계서, 소스코드 프로그램, 테스트 결과서)을 말하며, 구조가 눈에 보이지 않는 비가시성(Invisibility), 비선형적인 구조(Non-Linearity), 마모되지 않고 계속되어 변형(Does not wear out but change), 사람 중심의 작업(Human intensive)이라는 특징이 있음
- [소프트웨어 공학 개요] - 재사용 및 생산성 향상/소프트웨어 품질 향상/개발 및 유지보수 비용 절감/일정 준수를 목표로 개발, 운용, 유지보수 및 폐기에 대한 체계적인 공학적 접근 방법
- [소프트웨어 개발 프로세스와 생명 주기]
  - 프로세스: 고객의 요구사항을 만족하는 제품을 만들기 위한 절차/방법, 도구/장비, 인력의 통합
  - 소프트웨어 개발 프로세스: 소프트웨어 개발에 필요한 절차/방법, 도구/장비, 인력의 통합
  - 소프트웨어 개발 생명주기: 소프트웨어를 어떻게 개발할 것인가에 대해 정의한 최상위 수준의 프로세스(주먹구구식, 폭포수, 원형, 나선형 모델 등등)
- [V-Model] - 개발 생명주기의 각 단계와 그에 상응하는 소프트웨어 테스트 단계를 매핑한 모델
- **[A-SPICE]** - A-SPICE는 자동차 소프트웨어 개발 프로세스를 평가하기 위한 국제 표준으로, 조직의 프로세스 성숙도를 Capability Level 0~5로 구분하여 평가한다

  | Level   | 설명                                  |
  |:-------:|---------------------------------------|
  | Level 0 | 프로세스가 정의되어 있지 않음          |
  | Level 1 | 프로세스가 수행되고 있음 (비관리 상태) |
  | Level 2 | 계획되고 관리됨 (문서화 및 추적 가능)  |
  | Level 3 | 조직 차원의 표준 프로세스로 정립됨     |
  | Level 4 | 정량적 데이터 기반으로 관리됨          |
  | Level 5 | 지속적 개선 체계가 확립됨              |  
  
  실무에서는 일반적으로 Level 2 이상을 요구하는 경우가 많다.
    
  A-SPICE는 개발 활동을 여러 프로세스 영역(Process Area)으로 나누어 정의한다.
  그 중 핵심 영역은 SYS (System Level) 과 SWE (Software Level) 이다.
  
  **SYS – System Level**  - 시스템 단위(ECU 포함)의 상위 개발 단계에 해당한다.  
  | 코드   | 의미                     | 설명 |
  |--------|--------------------------|------|
  | SYS.1  | 시스템 요구사항 분석     | 이해관계자 요구사항을 시스템 요구사항으로 정의 |
  | SYS.2  | 시스템 아키텍처 설계     | 시스템 구성 요소 및 인터페이스 정의 |
  | SYS.3  | 시스템 통합 및 테스트    | 구성 요소 통합 후 시스템 수준 시험 |
  | SYS.4  | 시스템 검증              | 요구사항 충족 여부 검증 |

  **SWE – Software Level (임베디드 개발 핵심 영역)** - 임베디드 소프트웨어 개발자가 직접 수행하는 핵심 프로세스 영역
  | 코드   | 의미                         | 설명 |
  |--------|------------------------------|------|
  | SWE.1  | 소프트웨어 요구사항 분석     | 시스템 요구사항을 SW 요구사항으로 구체화 |
  | SWE.2  | 소프트웨어 아키텍처 설계     | SW 구성 요소 및 구조 정의 |
  | SWE.3  | 상세 설계 및 구현            | 모듈 설계 및 코딩 |
  | SWE.4  | 단위 테스트                  | 개별 모듈 기능 검증 |
  | SWE.5  | 소프트웨어 통합 테스트       | 모듈 통합 후 기능 시험 |
  | SWE.6  | 소프트웨어 검증              | 요구사항 대비 검증 |

  
- **[ISO 26262]** - 자동차 전기·전자(E/E) 시스템의 기능 안전(Functional Safety)을 위한 국제 표준.  
  브레이크, 조향, 에어백, ADAS 등 생명과 직결된 시스템이 포함된 자동차 환경에서 소프트웨어 오류는 인명 사고로 이어질 수 있으므로, ISO 26262는 **고장이 발생하더라도 위험을 허용 가능한 수준으로 감소시키는 것**을 목표로 한다.
  
  ISO 26262 핵심 개념  
  | 구분 | 내용 |
  |------|------|
  | 목적 | 자동차 전기/전자 시스템의 기능 안전 확보 |
  | 적용 대상 | 차량 내 E/E 시스템 및 소프트웨어 |
  | 핵심 개념 | 고장 발생 시에도 안전 상태 유지 (Fail-Safe) |
  | 위험 분석 | HARA(Hazard Analysis and Risk Assessment) 수행 |
  | 안전 등급 | ASIL A ~ D (위험도 기반 등급 체계) |

  ASIL (Automotive Safety Integrity Level) 등급 체계  
  | 등급 | 의미 |
  |------|------|
  | QM     | 일반 품질 관리 수준 (안전 요구 없음) |
  | ASIL A | 낮은 위험 수준 |
  | ASIL B | 중간 위험 수준 |
  | ASIL C | 높은 위험 수준 |
  | ASIL D | 최고 위험 수준 (가장 엄격한 안전 요구) |


  - [소프트웨어 설계] - 프로그램을 구현하기 전에 소프트웨어를 구성하는 요소와 구조를 정의해 구현의 기반을 만드는 활동
    - 소프트웨어 아키텍처 설계: 상위 수준에서 소프트웨어 구성요소들 간의 관계로 구성된 전체적인 구조를 설계하는 활동
    - 소프트웨어 상세 설계: 아키텍처 설계에서 도출된 소프트웨어 구성 요소(컴포넌트, 모듈)들의 내부 데이터와 알고리즘 로직 등을 설계하는 활동
  - [소프트웨어 구현 및 통합]
    - 소프트웨어 구현: 개별 소프트웨어 단위를 실행 가능한 형태로 구현하고 이를 문서화 하는 활동으로 프로그래밍이라고도 함
    - 소프트웨어 통합: 개발된 단위 모듈 소프트웨어들을 통합 계획에 따라 통합하여 완전한 소프트웨어 구조를 개발하는 활동(빅뱅, 하향식, 상향식, 지속적 통합 등)
  - [소프트웨어 검증 및 확인] - 제품이 올바르게 만들어지고 있는가, 올바른 제품을 만들고 있는가
  - [소프트웨어 테스팅] - 정상 조건 및 비정상 조건(결함이나 버그) 사이의 차이점을 발견하기 위하여 소프트웨어 항목을 분석하고, 분석된 항목의 특성을 평가하는 프로세스(단위, 통합, 시스템, 인스 테스팅)
  - [소프트웨어 형상 관리] - 형상 항목을 식별하고, 변경을 통제 및 처리 상태를 모니터링함으로써 요구사항에 부합하는지 확인하는 활동

  **이론**  
  - **[임베디드 시스템]** - 특정 기기에 MCU와 SW를 내장하여, 미리 정해진 고유한 기능만을 수행하도록 설계된 전용 컴퓨터 시스템
    - 특징 : 단일/특정 작업만 수행, 하드웨어와 펌웨어가 밀접하게 결합, 제한된 resource, 실시간성
    - 구조 : 입력 센서 - Main Processor - 출력 엑츄에이터  
  
  - **[CPU/GPU/MPU/MCU]**
    - CPU = Central Processing Unit  
    - GPU = Graphic Processing Unit  
    - MPU = Micro Processing Unit  
    - MCU = Micro Controller Unit : CPU + 메모리 + 인터페이스, 단독 동작이 가능하도록 만들어짐  

  - **[개발용 MCU 보드 종류]** - 초보용 MCU(아두이노, 라즈베리), 상용 MCU(ST(Nucleo 시리즈), 노르딕, 인피니언)  
  
  - **[Volatile keyword]** - 해당 변수를 최적화에서 제외하여 항상 메모리에 접근하도록 컴파일  
    - 사용법 : volatile data_type variable_name  
    - 필요성 : MIMO, 멀티 쓰레드 환경, 인터럽트 서비스 루틴  
  
  - **[MCU Bring-up]** - 전원이 인가된 MCU가 “의도한 소프트웨어를 실행할 수 있는 최소한의 정상 상태”까지 올라오는 과정  

  - **[I/O Access 방법]** - Special Instruction I/O, Memory-mapped I/O, Direct memory access (DMA)  

  - **[HAL]**
    - Basic HAL - 특정 MCU 아키텍처에 맞춰 하드웨어 기능을 직접 추상화한 기본 수준의 HAL (GPIO, SYSTICK, NVIC, RCC, FLASH etc)  
    - Generic HAL - 하드웨어 독립적인 공통 인터페이스를 정의하여 다양한 플랫폼에서 동일한 상위 코드를 가능하게 하는 HAL  

  - **[컴파일과 링킹]**
    - 컴파일(Compile) - 소스코드(.c)를 기계어 오브젝트 파일(.o)로 번역하는 과정
    - 링킹(Linking) - 여러 오브젝트 파일과 라이브러리를 연결해 실행 파일을 만드는 과정
    - 링커(Linker) - 오브젝트 파일들을 연결하고 주소를 배치해 최종 실행 파일을 만드는 프로그램  

  - **[GPIO]** - 마이크로컨트롤러의 핀을 입력 또는 출력으로 설정해 외부 장치와 디지털 신호를 주고받는 범용 입출력 인터페이스  

  - **[Pull up과 Pull down 저항]**
    - Pull up 저항 - 입력 핀이 아무것도 연결되지 않았을 때 기본값을 HIGH(1)로 유지하게 해주는 저항
    - Pull down 저항 - 입력 핀이 떠 있지 않도록 기본값을 LOW(0)로 유지하게 해주는 저항
    - 위 둘은 입력 핀이 아무것도 연결되지 않아 값이 불안정하게 변하는 floating 상태를 방지하기 위해 기본 전압(0 또는 1)을 안정적으로 정해주기 위해 사용한다.  

  - **[HAL]** - TM32의 레지스터를 직접 다루지 않고도 주변장치(GPIO, UART, SPI 등)를 쉽게 제어할 수 있도록 만든 하드웨어 추상화 라이브러리

  - **[임베디드 시스템 HW 구조]** - 메인 프로세서, 입력 센서, 출력 엑츄에이

### 10\. 임베디드 C 프로그래밍 코드 최적화 기법 <sub>(2026.02.26 ~ 2026.03.04)</sub>  
> **📝 학습 내용**  
> 메모리 구조와 TC275 부트 시퀀스, 코드 프로파일링과 컴파일러 최적화 기법을 이해하고, ROM/RAM 사용량 절감·실행 시간 개선을 위한 데이터 처리 및 흐름 제어 최적화 방법과 MISRA-C/BARR-C 기반의 안정적인 임베디드 C 코딩 규칙을 학습

<details>
  <summary>📚 상세 학습 내용 보기</summary>

---  

  **1. 프로그램 실행을 위한 메모리 구조**  
  - 메모리 구조 : <sub>High memory</sub> | 스택 | 힙 | 데이터 | 코드 | <sub>Low memory</sub>
    - 코드 영역 : 실행할 프로그램의 코드가 저장
    - 데이터 영역 : 전역 변수와 정적 변수가 저장 (프로그램 시작과 함께 할당 → 종료되면 소멸)
    - 힙 영역 : 사용자가 직접 관리할 수 있는 영역으로 메모리 공간이 동적으로 할당 및 해제, 낮은 메모리 주소로부터 높은 주소 방향으로 할당, 메모리 엑세스가 느림
    - 스택 영역 : 지역 변수와 매개변수가 저장되는 영역으로 높은 메모리 주소부터 낮은 주소의 방향으로 할당, 메모리 엑세스가 빠름  
    
  - ROM, RAM
    - RAM : CPU와 HDD 사이에 위치하여 자주 쓰는 데이터를 저장해 고속 처리 (Static RAM, Dynamic RAM)
    - ROM : 전원이 꺼져도 데이터가 유지되는 읽기 전용 비휘발성 메모리. (MASK ROM, Programmable ROM, etc.)
  
  **2. TC275 부트시퀀스**  
  - Linker : 불완전한 object 파일들을 합쳐 모든 코드와 데이터를 포함하는 새로운 object 파일을 생성해 내는 도구
  - Locate : 메모리에서 실행 가능하도록 코드와 데이터를 배치하여 최종 바이너리 이미지를 생성하는 도구

  **3. TC275 코드 프로파일링**
  - Disassembly를 활용한 코드 성능 파악

  **4. 컴파일러 최적화**
  - 코드 최적화 : 주어진 코드에 대해 동등한 의미를 가지면서 실행시간 및 메모리를 줄이는 것  
    - 핍홀 최적화 - 몇 개의 연속적인 명령어를 하나의 명령어나 더 짧은 명령어로 변환  
    - 지역 최적화 - 부분적인 관점에서 일련의 비효율적인 코드를 구분해내고 좀 더 효율적인 코드로 만드는 방법  
    - 루프 최적화 - 한 루프 안에서의 최적화 기법  
    - 전역 최적화 - 한 프로시저 내에서 일련의 비효율적인 코드를 구분해내고 좀 더효율적인 코드로 만드는 방법  
    - 프로시저 간 최적화 - 한 프로시저의 한계를 넘어 전체 프로그램에 적용되는 최적화  
    - 기계 종속적 최적화 - 기계의 특성에 따라 달라질 수 있는 성능을 최적화  
  - 기본 블록과 흐름 그래프 : 최적화 기법을 수행하기 위한 방법 중 일부  
    - 기본 블록 - 지역 최적화의 기본 단위
    - 흐름 그래프 - 기본 블록의 집합에 제어 흐름에 관한 정보를 추가하여 만든 유향 그래프  
  
  **5. 임베디드 C코드 최적화**
  - ROM 최적화 : 프로그램 코드, 상수, 초기화된 전역 변수와 정적 변수 최적화 즉, 코드와 상수를 줄이는 것
  - RAM 최적화 : 초기화되지 않은 전역변수와 정적 변수, 지역변수, 함수의 인자 및 함수 호출시 발생하는 context 최적화 즉, Stack의 사용량을 줄이는 것
  - 실행시간 최적화 : 인라인 함수 사용, 참조 테이블 및 인라인 어셈블리어 활용, 전역 변수 사용을 통한 함수 호출 오버헤드 회피, 폴링방식 및 정수 연산 활용  

  **6. Data Handling (데이터 처리)**
  - Data Types Usage : 올바른 Data Type을 사용하여, 불필요한 변수 크기로 인한 처리시간 증가를 예방  
  - Avoid Type Coversion : 처리를 위해 동일한 타입의 변수를 사용하여, 타입 변환으로 인한 처리시간 증가를 예방  
  - Signed & Unsigned의 구분  
    - Unsigned = 몫/나머지, loop cointer, array, indexing
    - Signed = 사칙 연산
  - Floats & Doubles : Float의 최대 값 = 0x7F7F FFFF, Double의 최대 값 = 0x7F7F FFFF FFFF FFFF, 불필요한 유형 변환이나 혼동을 피하기 위해 숫자 값 뒤에 문자 'f'를 지정
  - Constant : 데이터를 상수로 정의해 ROM 공간에 할당
  - Volatile : 컴파일러가 변수에 대한 최적화를 수행하지 못하도록 금지
  - Data Alignment - Arrangement & Paking : 메모리 structure를 고려한 변수를 선언
  - Pass bt Reference : 매개변수 수가 많을수록 각 함수 호출에서 push 및 pop 동작이 많기 때문에 오버헤드를 줄이기 위해 structure 참조를 파라미터로 전달하는 것이 더욱 효율적  
  - Initialization : Memory allocation 방법을 적절히 사용하여 RAM 사용량을 줄이는 것이 가능
  - Return 값 : 함수의 Return 값은 레지스터에 저장되며, Return data가 의도된 용도로 사용되지 않는다면 낭비가 됨
  - 비트 플래그 사용 : 상태를 나타내기 위한 플래그로 비트 연산(비트 플래그)을 사용  

  **7. Flow Control Handling (흐름제어 처리)**
  - if VS switch : 하나의 var를 받아 control flow를 짤 때에는 switch가 효율적, if는 값에 따라 시간이 달라지지만 switch는 lookup table 방식이기 때문
  - Inline : 컴파일러가 함수에 대한 모든 호출을 함수 코드의 복사본으로 대체하여 함수 호출과 관련한 오버헤드가 제거 (큰 함수를 인라인 할 경우 실행 파일의 크기가 너무 커짐)
  - Loop Hoisting : 컴퓨팅 시간 절약을 위해 후프 외부로 계산 이동
  - Loop overhead : MCU에는 양수에서 0으로 카운트다운 할 때 잘 작동, "미리 정의된 숫자"보다 "0"을 감지하는 것이 더 쉬움
  
  **8. Other Handling (기타 처리)**
  - Use of operators : 기존 연산자 적극 활용
  - Replacing, Integer Division with Multiplication : 정수 나눗셈은 모든 정수 연살 중 가장 느리므로, 식에 여러 나눗셈이 있는 경우 정수 나눗셈을 곱셈으로 변경
  - Use of Fomula : 곱셈을 최대한 피하고 덧셈으로 치환
  - Inline assembly : 어셈블리 명령들을 inline 함수로 작성
  - 부동소수점 연산 제거
  - 조건문 최적화

  **9. 신뢰성 있는 코드를 위한 가이드 라인**
  - [MISRA-C] : Moter Industry Software Reliablility Association, 자동차 산업 소프트웨어 신뢰성 협회로, 자동차 임베디드 소프트웨어의 결함을 줄이기 위해 탄생했지만 많은 개발자 스타일 가이드 라인으로 사용됨
  - [BARR-C] : Barr 그룹에서 발표한 자동차 임베디드 C코딩 표준으로 유지보수성과 이식성 향상이 목적
  - Line Widths : 프로그램 내 모든 줄의 너비는 최대 80자
  - Keywords to Avoid : auto/register 사용 불가, goto, continue 사용 지향
  - Braces : if, else, while 등의 코드 블록은 항상 중괄호로 둘러싸기 및 중괄호는 단독 줄에 표시
  - Parentheses : 수식은 명확성을 위해 괄효 사용
  - Common Abberviations : 약자는 되도록 '약어표'를 참조
  - Casts : 각 형변환에는 가능한 값 범위에서 적절한 동작을 보장하는 방법을 설명하는 주석이 포함되어야 함
  - Keywords to Frequent
    - static - 모듈 외부에 표시될 필요가 없는 모든 함수와 변수를 선언하는데 활용
    - const - 초기화 후 변경해서는 안되는 변수 선언, 수정해서는 안되는 call-by-reference 함수 매개변수 정의, 수정해서는 안되는 struct 또는 union의 필드 정의에 활용
    - volatile - interrupt service routune에서 엑세스할 수 있는 전역 변수 선언, 두 개 이상의 thread에서 엑세스할 수 있는 전역 변수 선언, memory-mapped I/O 주변 레지스터 세트에 대한 포인터 선언, delay loop counter 선언에 활용
  - Acceptable Formats : 일시적인 코드 주석 처리 안됨 (조건부 컴파일 기능을 활용하기)  
  - Locations and Content : 주석은 완전한 문장과 같은 들여쓰기 수준으로 모든 가정을 설명해야 함
    - WARNING - 이 코드를 변경하는데 위험이 있음을 경고
    - NOTE - chunk의 why에 대한 설명적 주석을 제공
    - TODO - 코드가 아직 작성 중임을 나타냄
  - Space : 대입/이항연산자 앞뒤 공백, 단항연산자는 피연산자쪽에 공백 없이, 삼항 연산자 구성 문자 앞뒤 공백 등
  - Alignment : 일련 선언 내 변수 이름은 첫 글자를 정렬, struct 및 union의 이름은 첫 글자를 정렬
  - Blank Lines : 한 줄의 코드에 두 개 이상의 문장이 포함되면 안되며 코드 블록의 앞뒤는 공백이 있어야 함
  - Indentation : 각 들여쓰기는 4자의 배수, 가독성 있게 들여쓰기 해야 함
  - Tabs : 탭 문자는 소스 코드 파일 내에 나타나지 않아야 함
  - Naming Conventions : 모든 모듈 이름은 소문자/숫자/밑줄로만 구성, 모든 모듈 이름의 처음 8자는 고유해야 함
  - Header Files : 각 소스 파일에는 정확히 하나의 헤더파일이 있어야 하며 헤더 파일은 항상 동일한 경로와 이름을 가져야 함, 각 헤더 파일에는 다중 포함을 방지하는 전처리기 가드가 포함되어야 함
  - File Templates : 헤더 파일과 소스 파일에 대한 템플릿 세트는 프로젝트 수준에서 유지 관리 되어야 함
  - Naming Conventions : structur, union, enum 등의 data type의 이름은 소문자와 밑줄로만 구성해야 하며, typedef를 통해 이름을 지정해야 함
  - Fixed-Width Integers : integer 값의 width가 중요한 경우 fixed width data types 중 하나를 사용해야 함
  - Signed and Unsigned Intergers : Bit-fiels는 signed integer types 내에 정의되어서는 안됨, 비트 연산자는 signed interger 연산에 사용해서는 안됨
  - Floating Point : floating point 상수와 변수 대신 가급적 Fixed-point math를 사용하는 것이 대안이 될 수 있음
  - Structuers and Unions : 컴파일러가 외부와 통신하는데 사용되는 struct 또는 unoin 내에 padding bytes가 삽입되지 않도록 주의, 컴파일러가 bit-fields 내 bits의 정해진 순서를 변경하지 않도록 적절한 주의
  - Booleans : bool 키워드로 선언, Non-boolean 값은 관계형 연산사를 사용해 boolean으로 변환해야 함
  - Naming Conventions : Procedure의 이름은 기존 라이브러리의 키워드 및 함수 이름에 겹칠 수 없으며, 함수 이름에 대문자를 포함하면 안됨, 매크로 이름에 소문자를 포함하면 안됨
  - Functions : 각 함수 길이는 100줄 이내로 제한하기 위해 노력해야 함, 종료 지점은 하나가 바람직, 모든 private functions 는 static으로 선언해야 함
  - Function-Like Macros : 동일한 동작을 수행하는 함수를 작성할 수 있는 경우 매개 변수화된 매크로를 사용하면 안됨
  - Threads of Execution : 실행 threads를 캡슐화하는 모든 함수의 이름의 끝은 "_thread" 로 지정
  - Interrupt Service Routines : ISRs은 일반적인 함수가 아니며 #pragma 또는 컴파일 전용 키워드를 통해 ISR임을 알려야 함, 관련 함수의 이름은 "_isr"로 끝나야 함
  - Naming Conventions : pointer 변수는 'p'로 시작해야 함, pointer-to-pointer는 'pp'로 시작해야 함, 전역 변수는 'g'로 시작해야 함, 3자 이상 31자 이내로 선언해야 함
  - Initialization : 모든 변수는 사용 전 초기화, 지역변수는 함수 맨 위에 모두 정의하는 것보다 필요할 때마다 정의하는 것이 좋음
  - Variable Declarations : 쉼표 연산자(,)는 변수 선언 내 사용 불가
  - Conditional Statements : if 및 else if 절 중 가장 짧은(코드행이) 항목은 먼저 배치, if 또는 else if 조건문 안에서 변수 할당을 하지 말아야 함
  - Switch Statements : 각 case는 코드 블록의 내용이 아닌 관련 case와 일치하도록 들여쓰기, 다음 case로 넘어가도록 설계된 경우 break가 없는 이유를 주석으로 달아야 함
  - Loops : Magic number를 초기값으로 사용하거나 while, do-while 등의 endpoint test에 사용하면 안됨, 무한 루프는 (;;)에 대한 제어 표현식을 통해 구현해야 함
  - Jumps : goto 문은 사용 제한
  - Equivalence Tests : 상수에 대해 변수의 동일성을 평가할 때 상수는 항상 등호 연산자 (==)의 왼쪽에 배치

  **1. 소프트웨어 개발과 요구공학**  
  - 요구사항 : 시스템이 수행할 작업 및 제공하는 서비스나 작동에 대한 제한 사항에 대한 설명, 이해관계자들이 제공될 시스템에 요구하는 기능과 제약사항을 정의 즉, _고객이 실제로 원하는 것_

  - 요구사항 관리
    - [정의] - 시스템 개발 과정에서 이해관계자가 요구한 기능·제약사항을 수집, 정리, 추적, 변경 관리하여 일관되게 유지하는 활동
    - [목적] - 고객이 실제로 원하는 기능과 제약을 정확히 반영하고 변경을 통제해 프로젝트 품질과 성공 가능성을 높이기 위함
  - 소프트웨어 개발 : 기술적 문제보다 인력과 요구사항 관리적 측면이 중요
    - [성공 원인] - 효과적인 경영 지원, 이해관계자들의 능동적 참여, 명확한 요구사항
    - [실패 원인] - 이해관계자들의 참여 부족, 의사소통 불명확, 불완전한 요구사항 정의
  - 소프트웨어 결함 : 불완전하고 불명확한 요구사항은 SW 결함을 발생 -> 결함 수정은 생명주기 후반에서 더 많은 노력을 요구 -> 요구사항 결함에 따른 SW 재작업 발생 -> 재작업 비용과 시간 추가
  - 명확한 요구사항 정의와 설계로 결함을 제거, 요구 사항 관리에 노력을 투자하는 것이 중요

  - 요구 공학
    - [정의] - 사용자 요구사항과 시스템 제약사항을 이해관계자와의 합의를 통해 추출, 분석, 명세, 검증하고 요구사항 변경을 관리하는 체계적인 공학적 활동
    - [특징]
      1. 이해관계자 중심성(사용자, 고객, 개발자 등 다양한 이해관계자의 요구를 반영하여 정의)
      2. 반복적·점진적 과정(요구사항은 한 번에 완성되지 않고 반복적으로 수정·보완됨)
      3. 의사소통 중심 활동(고객과 개발자 간 지속적인 협의와 합의 과정이 중요)
      4. 문서화 중심(요구사항을 명세서(SRS) 형태로 명확하게 문서화해야 함)
      5. 변경 관리 필요(개발 과정 중 요구사항이 변경될 수 있으므로 체계적인 변경 관리가 필요)
      6. 검증 가능성(요구사항은 테스트나 검증이 가능하도록 명확하게 정의되어야 함)
    - [프로세스] - 도출 -> 분석 -> 명세 -> 검증 -> 관리
    - [6 Questions]
      1. Who - 누가 시스템을 사용할 것인가?
      2. What - 시스템이 무엇을 해야 하는가?
      3. Why - 왜 이 시스템이 필요한가?
      4. Where - 시스템이 어디에서 사용되는가?
      5. When - 시스템이 언제 동작해야 하는가?
      6. How - 시스템이 어떻게 동작해야 하는가?
      
  **2. 비즈니스 중심 요구사항 추출**  
  - 요구사항 
    - [정의] - 이해관계자(고객, 사용자 등)로부터 시스템이 수행해야 할 기능과 제약사항을 찾아내고 수집하는 과정  
    - [계층] - 비즈니스 요구사항 - 사용자 요구사항 - 시스템 요구사항  
    - [원칙]
      1. 이해관계자 중심 - 모든 이해관계자의 요구를 균형 있게 반영
      2. 명확성 (Clarity) - 요구사항은 모호하지 않게 작성
      3. 완전성 (Completeness) - 필요한 요구사항이 빠짐없이 포함
      4. 일관성 (Consistency) - 서로 충돌하는 요구사항이 없어야 함
      5. 검증 가능성 (Verifiability) - 테스트로 확인 가능해야 함

  - 비즈니스 요구사항
    - [개요] - 조직이나 사업의 목표와 시스템 도입 목적을 상위 수준에서 설명하는 요구사항
    - [정의] - 조직의 비즈니스 목표를 달성하기 위해 시스템이 충족해야 하는 최상위 수준의 요구사항

  **3. 이해관계자 중심 요구사항 추출**  
  - 이해관리자
    - [개요] - 시스템 개발과 운영, 사용에 직·간접적으로 영향을 받거나 요구사항을 제시하는 개인 또는 조직
    - [관리] - 이해관계자의 요구와 기대를 파악하고 우선순위를 조정하며 지속적으로 의사소통하여 요구사항을 관리하는 활동

  - 이해관리자 요구사항 추출
    - [개요] - 이해관계자와의 상호작용을 통해 시스템에 필요한 기능, 서비스, 제약사항 등의 요구사항을 수집하는 활동
    - [추출 기법]
      1. Interview - 이해관계자와 직접 대화를 통해 요구사항을 수집하는 방법
      2. Brainstorming - 여러 사람이 자유롭게 아이디어를 제시하며 요구사항을 도출하는 방법
      3. Survey/Questionnaire - 설문지나 질문지를 통해 다수의 의견을 수집하는 방법
      4. Observation - 실제 업무나 시스템 사용 환경을 관찰하여 요구사항을 파악하는 방법

  - 이해관계자 중심 요구사항 추출
    - VORE (Viewpoint Oriented RE) - 다양한 이해관계자의 관점(Viewpoint)에서 요구사항을 식별하고 분석하여 요구사항을 도출하는 방법
    - GORE (Goal Oriented RE) - 이해관계자의 목표(Goal)를 중심으로 요구사항을 도출하고 이를 세분화하여 시스템 요구사항으로 구체화하는 방법

  **4. 가치 기반 요구사항 분석**  
  - 가치 기반 요구공학 : 시스템 개발 시 이해관계자에게 제공되는 가치(Value)를 기준으로 요구사항의 중요도와 우선순위를 결정하는 요구공학 접근 방법
  - 이해관계자 기대 관리 : 이해관계자의 요구와 기대 수준을 파악하고 조정하여 현실적인 목표와 요구사항으로 관리하는 활동  

  - 요구사항 모델링
    - [개요] - 요구사항을 이해하기 쉽도록 다이어그램이나 모델을 사용해 구조적으로 표현하는 활동
    - [모델 유형] - Function-Oriented Modeling, Information-oriented modeling, State-Oriented Model
    - [Use Case 기반 모델링] - 시스템 기능 및 요구사항 추출 행위를 모델링
  
  - 요구사항 우선순위
    - [개요] - 여러 요구사항 중에서 중요도, 가치, 비용, 위험 등을 고려하여 어떤 요구사항을 먼저 개발할지 결정하는 과정
    - [활동] - 요구사항의 중요도와 비즈니스 가치를 평가하고, 개발 비용·난이도·위험도 등을 고려하여 이해관계자와 협의 후 우선순위를 결정한다.
    - [기법]
      1. VOP - 요구사항이 제공하는 비즈니스 가치와 중요도를 기준으로 우선순위를 결정하는 방법
      2. Priority Matrix - 중요도와 비용(또는 긴급성) 등의 기준을 행렬 형태로 비교하여 우선순위를 정하는 방법
      3. AHP - 요구사항을 쌍대 비교하여 중요도를 계산하고 그 결과로 우선순위를 결정하는 기법

  - 요구사항 협상
    - [개요] - 이해관계자 간 상충되는 요구사항을 조정하고 합의를 통해 최종 요구사항을 결정하는 과정
    - [Triage] - 요구사항의 중요도, 비용, 위험 등을 고려하여 개발 여부와 우선순위를 결정하는 요구사항 선별 과정
    - [Basic Triage] - 요구사항을 중요도나 구현 가능성 기준으로 수용(Accept), 보류(Defer), 거절(Reject) 등으로 단순 분류하는 방법
    - [Advenced Triage] - 요구사항의 가치, 비용, 위험, 일정 영향 등을 종합적으로 분석하여 보다 체계적으로 우선순위와 개발 여부를 결정하는 방법

  **5. 품질 기반 요구사항 분석**  
  - SW 요구사항 명세
    - [개념] - 시스템이 수행해야 할 기능과 제약사항을 문서 형태로 체계적으로 기술한 것
    - [기준] - 요구사항은 명확성, 완전성, 일관성, 검증 가능성 등의 품질 기준을 만족하도록 작성해야 함
    - [표준] - 요구사항 명세 작성 시 IEEE 830, ISO/IEC/IEEE 29148 등의 표준을 참고하여 작성
    - [유형] - 기능 요구사항(Functional Requirements)과 비기능 요구사항(Non-functional Requirements)으로 구분됨
    - [정형화] - 요구사항을 일정한 형식과 규칙에 따라 명확하고 일관되게 표현하는 것
    - [상세화] - 상위 수준의 요구사항을 보다 구체적인 시스템 요구사항으로 세분화하는 과정
    - [평가 기준] - 요구사항의 명확성, 완전성, 일관성, 검증 가능성 등을 기준으로 품질을 평가
    - [추적] - 요구사항과 설계, 구현, 테스트 간의 관계를 연결하여 변경 및 관리가 가능하도록 하는 것
  
  - 품질 요구사항 명세
    - [전략] - 시스템의 성능, 신뢰성, 보안, 사용성 등 비기능적 품질 특성을 명확히 정의하고 측정 가능한 기준으로 요구사항을 명세하는 방법
    - [모델] - ISO/IEC 25010 등의 품질 모델을 활용하여 소프트웨어 품질 특성(성능, 신뢰성, 보안, 사용성 등)을 기준으로 요구사항을 구조화하는 방법

  ### 1. 정보보안 이해
  **[이론]**  
  **정보보안 중요성과 개요**  
  - 정보보안 중요성 및 기술 유형, 정보보안 분류, 관련 법
  - 최신 사이버 위협 동향
  - [정보보안] : 정보시스템 자원의 **3대 요소**를 보전하고자 하는 목표 달성을 위해 제공된 자동화된 정보시스템 보호
    - **3대 요소** - 기밀성, 무결성, 가용성
    - 3요소 외 추가 개념 - 인증, 책임
  
  **해킹의 유형**
  - 웜 (Worm) - 스스로 복제하여 네트워크를 통해 다른 시스템으로 자동 전파되는 악성 프로그램
  - 바이러스 (Virus) - 정상 프로그램에 붙어 실행될 때 감염을 확산시키는 악성 코드
  - 트로이 목마 (Trojan Horse) - 정상 프로그램처럼 위장해 사용자를 속이고 시스템 내부에서 악성 기능을 수행하는 프로그램
  - 스파이웨어 (Spyware) - 사용자 활동이나 개인정보를 몰래 수집하여 외부로 전송하는 악성 프로그램
  - 애드웨어 (Adware) - 사용자의 동의 없이 광고를 지속적으로 표시하거나 광고 수익을 위해 정보를 수집하는 프로그램
  - 봇 (Bot) - 감염된 컴퓨터를 원격에서 자동으로 제어하기 위해 설치되는 악성 프로그램
  - 봇넷 (Botnet) - 다수의 감염된 컴퓨터(봇)를 하나의 네트워크처럼 묶어 공격에 사용하는 시스템
  - 봇마스터 (Botmaster) - 봇넷을 원격에서 제어하며 공격 명령을 내리는 공격자
  - DDoS (Distributed Denial of Service) - 여러 대의 감염된 컴퓨터를 이용해 특정 서버나 네트워크에 과도한 트래픽을 보내 서비스를 마비시키는 공격
  - 랜섬웨어 (Ransomware) - 시스템 파일이나 데이터를 암호화한 뒤 이를 복구해 주는 대가로 금전을 요구하는 악성 코드
  - 키로거 (Keylogger) - 사용자가 입력하는 키보드 정보를 몰래 기록해 계정 정보 등을 탈취하는 프로그램
  - 백도어 (Backdoor) - 정상 인증 절차를 우회하여 시스템에 비밀리에 접근할 수 있도록 만든 통로
  - 악성코드와 오피스 문서 (Malicious Office Document) - 매크로나 스크립트를 이용해 문서를 열 때 악성 코드가 실행되도록 만든 오피스 파일 (예: Word, Excel, 매크로 공격)

  ### 2. 자동차 보안 이해를 위한 정보보안 기술
  **[이론]**  
  - 암호학 (Cryptography) : 통신과 정보를 안전하게 보호하기 위한 기법을 연구하고 실천하는 학문
  - 비대칭키 암호 (Asymmetric Key Cryptography) : 공개키와 개인키의 한 쌍을 사용하여 암호화와 복호화를 수행하는 방식 ex) RSA, ECC
  - 해시 함수 (Hash Function) : 임의 길이의 입력 데이터를 고정 길이의 값으로 변환하는 단방향 함수 ex) SHA-256, MD5
  - 대칭키 암호의 특징
    1. 동일한 비밀키를 암호화와 복호화에 모두 사용
    2. 연산이 빠르고 대용량 데이터 처리에 적합
    3. 송신자와 수신자 간 안전한 비밀키 공유가 중요
    4. 키가 노출되면 전체 통신 내용이 복호화될 수 있음
  - 대칭키 암호의 구성 요소 : 평문 (Plaintext), 암호화 알고리즘 (Encryption Algorithm), 비밀키 (Secret Key), 암호문 (Ciphertext), 복호화 알고리즘 (Decryption Algorithm)
  - 대칭키 암호의 요구사항 : 강력한 암호 알고리즘이 필요, 비밀키를 안전하게 공유하고 보호해야 함
  - 암호 시스템의 처리 방식 : 대체(Substitution), 치환(Transposition)
  - 평문 처리 방식 : 블록 암호 (Block Cipher), 스트림 암호 (Stream Cipher)
  - 무차별 대입 공격 (Brute-force Attack) : 가능한 모든 키를 시도하여 올바른 키를 찾는 공격 방식
  - Feistel Cipher Structure : 여러 라운드에 걸쳐 대체와 치환을 반복 적용하는 대칭키 암호 구조, 암호화와 복호화가 유사한 구조를 가짐
  - 블록 암호 설계 요소 : 블록 크기, 키 크기, 라운드 수, 서브키 생성 알고리즘과 라운드 함수의 복잡도
  - AES (Advanced Encryption Standard) : 미국 NIST가 DES를 대체하기 위해 선정한 대칭키 암호 표준으로, 128 / 192 / 256비트 키를 지원
  - SEED : 대한민국에서 개발된 128비트 블록 암호 알고리즘으로, 전자거래, 금융 서비스, 무선 통신 등 민감 정보 보호를 위해 설계됨
  - ARIA : 대한민국 국가 표준 블록 암호 알고리즘으로, 경량 환경과 하드웨어 구현 효율을 고려해 설계되었으며 128 / 192 / 256비트 키를 지원
  - 난수(Random Number) : 암호 시스템에서 키 생성, 세션 키 생성, 인증 과정 등에 핵심적으로 사용, 예측 가능한 난수는 전체 보안성을 약화시킬 수 있음
  - 난수의 특성 : 균등 분포 (Uniform Distribution), 독립성 (Independence), 예측 불가성 (Unpredictability)
    - PRNG (Pseudo Random Number Generator) : 알고리즘 기반의 의사난수 생성기
    - TRNG (True Random Number Generator) : 열잡음, 전압 변동, 양자 효과 등 자연 현상 기반의 진성난수 생성기
  - 하드웨어 기반 난수 생성 : CPU 내장 TRNG, TPM, HSM 등을 통해 안전한 키 생성과 암호 연산을 지원
  - 블록 암호 운용 모드
    - ECB (Electronic Codebook) : 각 블록을 독립적으로 암호화하는 방식, 동일한 평문 패턴이 암호문에 드러날 수 있어 보안성이 낮음
    - CBC (Cipher Block Chaining) : 이전 암호문 블록과 현재 평문 블록을 XOR한 뒤 암호화하는 방식, IV(Initialization Vector)를 사용하여 동일 평문의 반복 패턴 노출을 줄임
    - CFB (Cipher Feedback) : 블록 암호를 스트림 암호처럼 동작시키는 방식, 실시간 처리에 적합하며 별도의 패딩이 필요 없음
    - CTR (Counter Mode) : 카운터 값을 암호화한 결과와 평문을 XOR하여 암호문을 생성하는 방식, 병렬 처리에 유리하고 현대 프로토콜에서 널리 사용됨
  - IV와 Nonce : IV(초기화 벡터)는 동일한 키와 평문으로도 서로 다른 암호문이 생성되도록 도와주는 값, CTR 모드에서는 Nonce와 Counter를 조합하여 블록별 고유 입력 값을 생성
  - 전자서명 (Digital Signature) : 메시지의 무결성과 송신자 인증, 부인 방지를 제공하는 기술, 일반적으로 해시값을 생성한 뒤 개인키로 서명하고 공개키로 검증
  - 메시지 인증 코드 (MAC) : 송신자와 수신자가 공유한 비밀키를 이용해 메시지 무결성과 인증을 제공하는 방식
  - 공개키 기반구조 (PKI, Public Key Infrastructure) : 공개키 인증서 발급과 신뢰 체계를 관리하는 구조, 인증기관(CA)을 통해 공개키의 신뢰성을 검증
  - 인증서 (Certificate) : 공개키와 소유자 정보를 포함하며 인증기관의 전자서명으로 위·변조 여부를 검증할 수 있는 전자 문서
  - TLS / HTTPS : 네트워크 통신 구간의 기밀성과 무결성을 보장하기 위한 프로토콜, 공개키 암호, 대칭키 암호, 해시 및 인증서 기술이 함께 활용

  **[실습]**  
  - 취약한 C 프로그램을 작성하고 버퍼 오버플로 발생 가능 구조를 확인
  - gcc와 gdb를 이용해 프로그램을 컴파일하고 디버깅 환경을 구성
  - 브레이크포인트를 설정한 뒤 입력값에 따라 스택 메모리와 레지스터 값이 어떻게 변하는지 확인
  - 정상 길이 입력과 초과 길이 입력을 비교하여 버퍼 범위 초과 시 인접 메모리 영역이 손상되는 과정을 분석
  - strcpy 호출 전후의 스택 구조를 추적하며 버퍼, 프레임 포인터, 반환 주소의 배치를 관찰
  - 취약한 코드가 안전하지 않은 이유를 확인하고 입력 검증의 필요성을 학습
  - SetUID 환경과 결합될 경우 취약점의 위험성이 더욱 커질 수 있음을 이해
  - 단순한 프로그램 취약점이 실제 권한 상승과 시스템 침해로 이어질 수 있음을 사례 중심으로 학습
  - 소프트웨어 보안 취약점은 단순 문법 실수가 아니라 시스템 전체 보안에 영향을 미치는 핵심 문제임을 이해

  ### 3. 자동차 보안 이해  
  **[이론]**  

  - 자산 (Asset) : 개인이나 조직이 보호해야 할 경제적·기능적 가치가 있는 대상
  - 위협 (Threat) : 자산에 손실이나 피해를 발생시킬 수 있는 행위나 사건
  - 취약점 (Vulnerability) : 위협이 실제 피해로 이어질 수 있게 만드는 시스템의 약점
  - 위험 (Risk) : 자산, 위협, 취약점이 결합되어 실제 손실이 발생할 가능성과 영향
  - CVSS (Common Vulnerability Scoring System) : 소프트웨어 취약점의 심각도를 정량적으로 평가하기 위한 표준 체계
    - [목적] - 취약점의 심각도를 일관된 기준으로 평가, 취약점 간 우선순위 비교 가능, 패치 및 대응 우선순위 결정 지원
    - [버전]
      1. CVSS v1 - 초기 표준
      2. CVSS v2 - 평가 기준 보완
      3. CVSS v3 / v3.1 - 공격 난이도, 권한 요구, 사용자 상호작용 등 현실적 요소를 더 정교하게 반영
    - [점수 체계] - 0.0 ~ 10.0 범위로 평가, 낮음, 중간, 높음, 심각 단계로 분류
    - [평가 요소]
      - Base Metric
        - 공격 벡터 (AV, Attack Vector) : 공격자가 취약점에 도달하는 방식
        - 공격 복잡도 (AC, Attack Complexity) : 공격 성공에 필요한 난이도
        - 필요 권한 (PR, Privileges Required) : 공격에 필요한 사전 권한 수준
        - 사용자 상호작용 (UI, User Interaction) : 공격 성공에 사용자 행동이 필요한지 여부
        - 범위 (S, Scope) : 취약점 악용 결과가 다른 보안 경계까지 확장되는지 여부
        - 기밀성 (C, Confidentiality) : 정보 유출 영향
        - 무결성 (I, Integrity) : 데이터 변조 영향
        - 가용성 (A, Availability) : 서비스 중단 영향
      - Temporal Metric
        - 공격 코드 성숙도
        - 교정 수준
        - 보고 신뢰도
      - Environmental Metric
        - 실제 운용 환경의 중요 자산 특성과 보호 요구 수준을 반영하여 위험도를 조정

  - CVE (Common Vulnerabilities and Exposures) : 공개적으로 알려진 보안 취약점에 부여되는 고유 식별자
  - CWSS (Common Weakness Scoring System) : 취약점이 아니라 소프트웨어 내부 약점 자체의 우선순위를 평가하는 체계로, CVSS가 “발견된 취약점의 심각도”를 평가한다면, CWSS는 “내재된 약점의 위험성”을 본다는 점에서 차이가 있음

  - 차량 전기/전자 아키텍처 (E/E Architecture) : 차량 내부의 전기·전자 시스템과 ECU(Electronic Control Unit)들이 어떻게 구성되고 연결되는지를 정의한 구조
    - [발전 단계]
      1. Distributed Architecture (분산형 아키텍처) - 초기 차량 구조로 기능별 ECU가 개별적으로 존재하는 구조
      2. Domain Architecture (도메인 아키텍처) - 차량 기능을 도메인 단위로 묶어 제어하는 구조 (ex Powertrain Domain, ADAS Domain, Infotainment Domain)
      3. Zonal Architecture (존 아키텍처) - 차량의 물리적 위치 기준으로 ECU를 구성하는 구조
      4. Centralized Architecture (중앙집중형 아키텍처) - 고성능 중앙 컴퓨터가 차량 대부분 기능을 처리하는 구조, SDV(Software Defined Vehicle)의 핵심 구조
    - ECU (Electronic Control Unit) : 차량 내 특정 기능을 제어하는 임베디드 컴퓨터 시스템 (ex 엔진 제어 ECU, 브레이크 ECU, 인포테인먼트 ECU)

  - 차량 네트워크 구조 : 차량 내부의 여러 ECU들은 다양한 통신 네트워크를 통해 연결되어 협력적으로 동작한다.
    - CAN (Controller Area Network) - 차량 내부에서 가장 널리 사용되는 통신 프로토콜, ECU 간 실시간 데이터 교환을 위해 설계된 버스 기반 네트워크
    - LIN (Local Interconnect Network) - 비교적 단순한 센서 및 액추에이터 제어를 위한 저속 네트워크, CAN보다 비용이 낮고 구조가 단순
    - FlexRay - 고속·고신뢰 통신이 필요한 안전 시스템에 사용되는 차량 네트워크
    - Automotive Ethernet - ADAS 및 자율주행 시스템에서 대용량 데이터를 처리하기 위해 사용되는 고속 네트워크
    - 차량 네트워크 특징 - ECU 간 메시지 기반 통신, 실시간 제어 요구, 높은 안정성과 신뢰성 요구

  - Gateway ECU : , Gateway ECU는 서로 다른 차량 네트워크(CAN, LIN, Ethernet 등)를 연결하는 ECU,  네트워크 간 메시지를 라우팅하고 통신을 관리하는 역할 수행, 외부 네트워크와 차량 내부 네트워크 사이에서 보안 경계 역할 수행
  - 차량 센서 시스템 : 차량은 다양한 센서를 이용해 주변 환경을 인식한다.
    - 예)  Camera, Radar, LiDAR, Ultrasonic Sensor, GPS
    - 이러한 센서 데이터는 ADAS 및 자율주행 시스템에서 사용되며, 센서 데이터 위·변조는 차량 안전에 직접적인 영향을 줄 수 있다.

  - 차량 보안 관점에서의 공격 표면 (Attack Surface) :  차량이 네트워크 기반 시스템으로 발전하면서 외부 공격 경로가 증가하였다.
    - 예) OBD-II 포트, 인포테인먼트 시스템, Bluetooth / Wi-Fi, Telematics (LTE/5G 연결), OTA 업데이트 시스템, 충전 인프라 (EV Charger)
    - 차량 내부 네트워크는 기본적으로 신뢰 기반 설계로 만들어졌기 때문에  
    외부에서 접근이 가능해질 경우 보안 취약점이 발생할 수 있다.

  - 차량 보안 기술 : 차량 시스템을 보호하기 위해 다양한 보안 기술이 적용된다.
    - Secure Boot - ECU 부팅 시 실행되는 소프트웨어의 무결성을 검증하는 기술
    - Secure Flashing - ECU 소프트웨어 업데이트 시 인증된 소프트웨어만 설치되도록 하는 기술
    - Hardware Security Module (HSM) - 암호 연산 및 키 관리를 수행하는 보안 전용 하드웨어
    - Intrusion Detection System (IDS) - 차량 네트워크에서 비정상적인 메시지를 탐지하는 보안 시스템
    - Gateway Firewall - 차량 네트워크에서 허용되지 않은 메시지를 차단하는 보안 기능

  - OTA (Over-the-Air) 보안 :  OTA는 차량 소프트웨어를 원격으로 업데이트하는 기술이다.
    - [보안 요구사항] - 업데이트 파일 무결성 검증, 업데이트 소프트웨어 인증, 안전한 통신 채널 사용, 업데이트 실패 시 롤백 기능 제공
    - OTA 보안이 취약할 경우 공격자가 차량 소프트웨어를 변조할 위험이 있다.

  - 자동차 사이버보안 표준
    - ISO 21434 - 차량 사이버보안 관리 체계를 정의한 국제 표준
    - UNECE R155 - 차량 사이버보안 관리 시스템(CSMS) 규정
    - UNECE R156 - OTA 업데이트 관리 규정

  - 차량 시스템은 단순 정보 시스템이 아니라 물리적 안전과 직결되는 사이버-물리 시스템(CPS)이다. 보안 취약점이 발생할 경우 차량 제어 기능 변조, 운전자 안전 위협, 개인정보 유출, 서비스 장애 등의 문제가 발생할 수 있다. 따라서 차량 소프트웨어 개발에서는 Secure Coding, Secure Communication, Secure Update, 보안 취약점 관리(CVE / CVSS) 등을 함께 고려해야 한다.

  - 정보보안 3대 요소
    - 기밀성 (Confidentiality) : 허가된 사용자만 데이터를 읽을 수 있어야 함
    - 무결성 (Integrity) : 데이터가 전송 과정에서 변조되지 않아야 함
    - 가용성 (Availability) : 필요한 시점에 서비스와 데이터가 정상 제공되어야 함
  - HMAC (Hash-based Message Authentication Code) : 해시 기반 메시지 인증 코드, 비밀키와 해시 함수를 함께 사용하여 메시지 무결성과 인증을 보장하는 방식
  - AES의 ECB 모드 : 데이터를 16바이트 블록 단위로 독립적으로 암호화하는 방식, 동일한 평문 블록은 동일한 암호문 블록으로 변환되어 패턴이 드러날 수 있음, 이미지나 반복 데이터 암호화 시 구조적 패턴이 노출되는 취약점이 존재
  - ECB 모드의 한계 : 블록 간 연관성이 없어 평문 구조가 암호문에 반영될 수 있음, 암호화는 수행되지만 보안성이 충분하지 않아 실무 사용에 부적절
  - CTR 모드 : 카운터 값을 이용해 블록별로 서로 다른 키스트림을 생성하는 방식, ECB의 반복 패턴 문제를 완화할 수 있음, 병렬 처리에 유리하고 속도가 빠름
  - AES-GCM (AEAD) : AES-CTR 기반의 기밀성과 GHASH/GMAC 기반의 무결성 검증을 결합한 방식, 암호문뿐 아니라 AAD(Additional Authenticated Data)까지 함께 보호 가능, 태그(Tag)를 통해 데이터 변조 여부와 유효한 송신자 여부를 검증할 수 있음
  - AAD (Associated Authenticated Data) : 암호화하지는 않지만 무결성 보호가 필요한 데이터, 메시지 헤더나 프로토콜 정보처럼 평문 상태로 전달되면서도 변조는 방지해야 하는 데이터에 사용
  - GCM의 보안 특성 : 데이터 기밀성 보장, 인증 태그를 통한 무결성 검증, 키를 아는 발신자만 유효한 태그를 생성할 수 있으므로 인증 기능 제공
  - Curve25519 / X25519 : 빠르고 안전하며 구현 실수 가능성이 적은 타원곡선 기반 공개키 알고리즘, X25519는 Curve25519 위에서 동작하는 키 교환 알고리즘으로, 두 노드가 안전하게 공유 비밀을 생성하는 데 사용, 공개키 암호는 대칭키 암호보다 느리므로 실제 통신에서는 공개키 방식으로 세션 키를 합의한 뒤 대칭키 암호를 사용하는 구조가 일반적

  **[실습]**  
  - HMAC을 이용하여 메시지에 대한 인증 코드 생성 실습 수행
  - AES-ECB 방식으로 평문을 암호화한 뒤, 반복되는 평문 블록이 암호문에서도 반복 패턴으로 드러나는 현상을 확인
  - 이미지 파일을 ECB 방식으로 암호화하여, 암호화 후에도 원본 구조가 유추될 수 있는 문제를 확인
  - 반복 문자열을 소켓 통신으로 전송하고 ECB 암호문 내 반복 패턴이 그대로 나타나는 것을 Wireshark로 관찰
  - 같은 데이터를 CTR 모드로 변경해 암호화함으로써 ECB에서 드러나던 패턴이 사라지는 것을 비교
  - AES-GCM을 로컬 환경에서 실행하여 평문, 키, Nonce, AAD, Ciphertext, Tag, 복호화 결과를 확인
  - AES-GCM 기반 소켓 통신을 구현하여 노드 A와 노드 B 간 암호화된 메시지 송수신 실습 수행
  - 평문 통신과 AES-GCM 적용 통신을 비교하고, Wireshark를 통해 평문은 쉽게 도청 가능하지만 암호 적용 시 직접적인 내용 확인이 어렵다는 점을 검증
  - 보안 통신은 단순 암호화만으로 충분하지 않고, 무결성 검증과 인증 태그까지 함께 고려해야 안전한 통신이 가능하다는 점을 학습

  ### 4. 시큐어코딩의 중요성 이해 및 OWASP TOP 10 기반 실습  
  **[이론]**

  - 시큐어코딩 (Secure Coding)
    - [정의] - 개발 단계에서 설계 및 구현상의 보안 취약점을 최소화하기 위해 보안 고려사항을 반영하여 코드를 작성하는 방법
    - [목표] - 기능적 안전성(Safety)과 정보보호(Security)를 동시에 달성하는 것
    - [핵심 목표 (CIA Triad)]
      1. 기밀성 (Confidentiality) - 인가된 사용자만 데이터에 접근 가능하도록 하여 정보 유출을 방지
      2. 무결성 (Integrity) - 데이터가 변조되지 않고 정확한 상태를 유지하도록 보장
      3. 가용성 (Availability) - 인가된 사용자가 언제든지 정상적으로 시스템을 사용할 수 있도록 보장

  - 보안 취약점의 비용 증가 (Shift Left) : 취약점은 발견 시점이 늦어질수록 수정 비용이 크게 증가한다.
  - Shift Left : 보안 점검과 테스트를 개발 초기 단계에서 수행하는 접근 방식
  - 소프트웨어 개발 생명주기 (SDLC) : 요구사항 -> 설계 -> 구현 -> 테스트 -> 배포 -> 운영
    - 운영 단계에서 발견된 취약점은 요구사항 또는 설계 단계에서 발견된 취약점보다 수정 비용이 훨씬 크다.
  
  - MS-SDL (Microsoft Security Development Lifecycle) : 마이크로소프트에서 개발한 보안 중심 소프트웨어 개발 방법론
    - [목표] - 소프트웨어 보안 사고 예방, 시스템 신뢰성 및 보안성 향상
    - [특징] - 개발 초기 단계부터 보안 고려, 보안 활동을 SDLC에 통합
    - [주요 단계]
      1. 교육 (Training) - 개발팀에 보안 교육 수행
      2. 요구사항 / 계획(Requirements) - 보안 요구사항 정의 및 보안 위험 평가 수행
      3. 설계 (Design) - 보안 설계 검토 및 위협 모델링 수행
      4. 구현 (Implementation) - 시큐어 코딩 가이드 적용 및 정적 분석 도구 사용
      5. 검증 (Verification) - 동적 분석 및 침투 테스트 수행
      6. 배포 (Release) - 최종 보안 승인 및 보안 문서 작성
      7. 대응 (Response) - 취약점 대응 및 보안 업데이트 수행
    - [핵심 보안 활동]
      1. 위협 모델링 (Threat Modeling) - 시스템 설계 단계에서 발생할 수 있는 보안 위협을 분석하는 과정 
      2. Security Bug Bar - 제품 출시 전에 반드시 해결해야 하는 보안 취약점의 최소 기준 정의하여 심각한 취약점이 포함된 상태로 제품이 배포되는 것을 방지
      3. Final Security Review (FSR) - 제품 출시 직전에 수행되는 최종 보안 검토 절차로 모든 보안 활동 수행 여부 확인하고 잔여 보안 위험 평가하기 위함
  
  - 소프트웨어 개발 보안 7대 취약점 분류 : 국내에서는 KISA 시큐어코딩 가이드를 기반으로 분류
    1. 입력 데이터 검증 및 표현 - 외부 입력값에 대한 유효성 검증 수행 (SQL Injection, XSS, 경로 조작, 정수 오버플로우)
    2. 보안 기능 - 인증 / 접근제어 / 암호화 기능의 안전한 구현 (취약한 암호화 알고리즘 사용, 하드코딩된 비밀번호, 부적절한 인증 처리)
    3. 시간 및 상태 : 동시성 문제 또는 경쟁 상태(Race Condition) 관련 취약점 (예측 가능한 난수, 시간 기반 인증 우회)
    4. 에러 처리 : 오류 발생 시 민감한 정보가 노출되지 않도록 처리 (스택 트레이스 노출, 내부 경로 정보 노출)
    5. 코드 오류 : 개발자의 구현 실수로 발생하는 취약점 (Null Pointer Dereference, 메모리 누수, 자원 반환 실패)
    6. 캡슐화 : 객체 내부 데이터 보호 (public 변수 사용, 내부 데이터 외부 노출)
    7. API 오용 : 보안 관련 API를 잘못 사용하여 발생하는 취약점 (eval() / exec() 사용, 안전하지 않은 시스템 호출)

  - 언어별 주요 보안 취약점 특징
    - <C>
      - [주요 위협 취약점] - 버퍼 오버플로우, 메모리 누수, 포맷 스트링 공격
      - [대응 방법] - 경계 검사 함수 사용, 입력값 검증, 안전한 문자열 함수 사용
    - <Java>
      - [주요 위협 취약점] - 직렬화 취약점, 웹 기반 공격 (XSS / SQL Injection)
      - [대응 방법] - 입력값 검증, 객체 캡슐화 유지, 안전한 API 사용
    - <Python>
      - [주요 위협 취약점] - eval() / exec() 코드 실행 취약점, pickle 역직렬화 취약점, 명령어 실행 취약점 (Command Injection), 입력값 검증 부족
      - [대응 방법] - 사용자 입력값 검증, eval / exec 사용 제한, 안전한 직렬화 방식 사용, subprocess 사용 시 인자 검증

  - 해외 시큐어 코딩 가이드
    - CERT Secure Coding Standards (CERT 시큐어코딩 표준)
      - [정의] - CERT (Computer Emergency Response Team)는 미국 카네기멜론대학교 산하 소프트웨어 공학 연구소(SEI)에서 운영, 코딩 단계에서 발생할 수 있는 보안 취약점의 근본 원인을 제거하기 위한 표준화된 코딩 규칙 제공
      - [목적] - 메모리 안전성, 오류 처리 등 언어 자체의 위험 요소를 제거하여 소프트웨어의 안전성, 신뢰성, 보안성을 확보
      - [언어별 규칙] - C, C++, Java, Perl, Python, Android 등 주요 언어별 구체적인 규칙과 권고 지침 제공
      - [세부 내용] - 버퍼 오버플로우, 정수 오버플로우, 경쟁 조건(Race Condition), 메모리 누수 등 언어 특화 취약점에 대한 대응 규칙 제공
      - [활용] - 국방, 금융, 의료 등 안전이 중요한 시스템 개발에서 활용되며 정적 분석 도구의 검사 기준으로 사용
      - [연계성] - CWE(Common Weakness Enumeration)와 연계되어 취약점을 체계적으로 분류

    - OWASP Top 10 (웹 애플리케이션 10대 보안 위험)
      - [정의] - OWASP (Open Web Application Security Project)는 웹 애플리케이션 보안 분야에서 가장 영향력 있는 국제 보안 커뮤니티, OWASP Top 10은 코딩 규칙이 아니라 웹 애플리케이션에서 가장 치명적이고 빈번하게 발생하는 보안 위험 목록을 제시
      - [목적] - 개발자와 보안 전문가에게 주요 보안 위험에 대한 인식을 높이고 대응 우선순위를 제공
      - [주기] - 약 3~4년 주기로 업데이트 (최근 버전: 2021)
      - [주요 취약점 예시] - Injection, Broken Access Control, Cryptographic Failures, Security Misconfiguration, Cross Site Scripting (XSS), Identification and Authentication Failures
      - [활용] - 웹 및 API 개발 시 보안 점검의 기본 기준으로 활용

    - MISRA C (Motor Industry Software Reliability Association C)
      - [정의] - 자동차 산업 및 항공, 의료 등 안전이 중요한 시스템에서 사용되는 C 언어 코딩 표준
      - [목적] - C 언어 코드의 안전성, 보안성, 이식성을 향상
      - [특징] - C 언어의 위험하거나 모호한 기능 사용을 제한
      - [주요 적용 언어] - C (C90, C99, C11)
      - [핵심 원칙] - Undefined Behavior 금지, Implementation-Defined Behavior 최소화, 코드 가독성 향상, 유지보수성 강화
      - [주요 대응 취약점] - 포인터 오류, 버퍼 오버플로우, 메모리 오류

    - AUTOSAR C++ Coding Guideline
      - [정의] - AUTOSAR 환경에서 C++ 코드의 안전성, 품질, 보안을 확보하기 위한 코딩 규칙, MISRA C++ 가이드를 기반으로 설계
      - [주요 대상] - 자동차 소프트웨어 개발 환경
      - [사용 언어] - C++14 / C++17
      - [핵심 원칙] - 객체지향 기능의 안전한 사용, 메모리 관리 안정성 확보, 타입 안정성(Type Safety) 보장, 보안 취약점으로 이어질 수 있는 C++ 기능 제한
      - [권장 사항] - smart pointer 사용, 자원 관리 자동화, 안전한 상속 및 다형성 구조 사용

  - SQL Injection (SQL 인젝션)
    - [개념] - SQL Injection은 사용자 입력값을 적절히 검증하지 않고, SQL 쿼리에 직접 포함시킬 때 발생하는 취약점이다. 공격자는 입력값을 조작하여 데이터베이스 쿼리를 의도와 다르게 실행시킬 수 있다.
    - [원리] - 입력값에 SQL 문법을 삽입하여 조건을 항상 참으로 만들거나 쿼리를 변형
      - 예시 입력  
        ```
        ' OR '1'='1
        ```  
      - 예시 실제 실행 쿼리
        ```
        SELECT * FROM users WHERE id = '' OR '1'='1'
        ```  
      - 위 쿼리는 항상 참이므로 인증을 우회하는 것이 가능하다
    - [주요 공격 유형]
      1. 인증 우회 (Authentication Bypass) - 로그인 없이 접근 가능
      2. 데이터 조회 (Data Extraction) - DB 내부 정보 탈취
      3. 데이터 변조 (Data Manipulation) - 데이터 수정 / 삭제 가능
      4. Blind SQL Injection - 결과가 보이지 않아도 참/거짓 기반으로 정보 추출
    - [취약점 발생 원인] - 사용자 입력값 검증 부족, 문자열 기반 SQL 쿼리 생성, 동적 쿼리 사용, 입력값 필터링 미흡
    - [대응 방법 (Secure Coding)]
      1. Prepared Statement (파라미터 바인딩) - SQL 구조와 입력값을 분리하여 공격 차단
      2. 입력값 검증 - 허용된 값만 통과 (화이트리스트 방식)
      3. ORM 사용 - 직접 SQL 작성 최소화
      4. 최소 권한 원칙 - DB 접근 권한 제한
      5. 에러 메시지 숨김 - 내부 SQL 정보 노출 방지
    - [보안 관점 핵심 정리] - SQL Injection은 가장 대표적인 웹 취약점, 입력값 검증과 안전한 쿼리 사용으로 대부분 방어 가능, OWASP Top 10의 Injection 항목에 해당

  **[실습]**  
  - 취약한 SQL 쿼리 구조를 구성하여 사용자 입력값이 그대로 반영되는 구조 확인  
  - 입력값에 ' OR '1'='1 과 같은 조건을 삽입하여 인증 우회 공격 재현  
  - SQL Injection을 통해 전체 사용자 데이터 조회 가능함을 확인  
  - 공격 입력 → 쿼리 변형 → DB 실행 → 결과 반환의 공격 흐름 이해  
  - 문자열 기반 동적 SQL 쿼리 작성이 취약점의 주요 원인임을 확인  
  - 파라미터 바인딩(Prepared Statement)을 적용하여 입력값과 SQL 구조 분리  
  - Secure Coding 적용 시 동일 공격이 차단되는 것을 검증  
  - Django ORM 사용 시 SQL Injection이 자연스럽게 방어됨을 확인  
  - 입력값 검증, ORM 사용, 최소 권한 원칙 등의 보안 코딩 필요성 학습  

  ### 5. AUTOSAR C++ 시큐어코딩
  **[이론]**  
  - AUTOSAR C++ 가이드 : 차량 소프트웨어의 안정성과 보안을 위한 C++ 코딩 규칙  
    - [목적] - Undefined Behavior 제거, 런타임 오류 방지, 메모리 안전성 확보, 보안 취약점 사전 제거  
    - [핵심 원칙] - 명확한 코드 작성 (Explicitness), 초기화 강제 (Initialization), 안전한 메모리 사용, 예외 및 오류 처리 명확화  
    - [주요 규칙] - 초기화되지 않은 변수 사용 금지, 배열 범위 초과 접근 금지, 포인터 연산 최소화, nullptr 사용 권장, 암묵적 형 변환 최소화, 전역 변수 사용 제한, 매크로 사용 제한, 동적 메모리(new/delete) 사용 최소화  
    - [보안 관점] - 차량은 CPS (Cyber-Physical System), 소프트웨어 오류 → 실제 물리적 사고로 이어질 수 있음  
  - 차량 사이버보안 규정 (UN R155) : UNECE에서 제정한 차량 사이버보안 규정으로, 차량 제조사는 보안 관리 체계를 의무적으로 구축해야 함  
    - [주요 개념] - 차량 보안을 “제품 기능”이 아니라 “관리 체계”로 접근, 차량 전체 생애주기(Lifecycle)에 걸친 보안 요구  
    - [핵심 요구사항]
      1. CSMS (Cyber Security Management System) - 정책, 프로세스, 책임 구조 포함 조직 차원의 보안 관리 체계 구축
      2. 위험 관리 (Risk Management) - 자산 식별, 위협 분석 (Threat Analysis), 취약점 분석 (Vulnerability Analysis), 위험 평가 (Risk Assessment)
      3. 보안 대응 (Incident Response) - 침해 사고 대응 체계 필요, 로그 수집 및 분석
      4. 업데이트 보안 (Secure Update) - OTA 업데이트 시 무결성 검증 필수, 악성 코드 삽입 방지  
    - [핵심 포인트] - “보안은 개발 이후가 아니라 설계 단계부터 포함되어야 한다”

  - 메시지 인증 (HMAC) : 비밀 키 기반 해시 인증 방식으로 메시지 무결성 보장, 송신자 인증 가능, 동일 입력 + 동일 키 → 동일 결과와 같은 특징을 가짐
  - 대칭키 암호 (AES) : 블록 기반 대칭키 암호 알고리즘으로 고정 길이 블록 처리, 동일 입력 → 동일 출력 (모드에 따라 달라짐)과 같은 특징을 가짐
  - ECB (Electronic Codebook) : 각 블록 독립 암호화 동일 평문 → 동일 암호문
  - CTR (Counter Mode) : nonce + counter 기반 스트림 암호  
    - [특징] - 동일 평문 → 다른 암호문 가능, XOR 기반
    - [장점] - 패턴 없음, 병렬 처리 가능
    - [한계] - 무결성 제공 안 함  
  - GCM (Galois/Counter Mode) : CTR + 인증 기능 
    - [구성 요소] - Plaintext, Key, Nonce, AAD, Ciphertext, Tag  
    - [특징] - 기밀성 + 무결성 제공, 위변조 검증 가능  

  - 네트워크 보안 관점
    - 평문 통신 - 패킷 그대로 노출, Wireshark로 분석 가능
    - 암호화 통신 - 내용 확인 불가, 도청 어려움

  - 핵심 비교
    - ECB → 패턴 노출 (취약)
    - CTR → 기밀성만 제공
    - GCM → 기밀성 + 무결성

  **[실습]**
  - AUTOSAR C++ 가이드 기반으로 초기화되지 않은 변수, 배열 범위 초과, 포인터 사용 등 위험 코드 패턴을 분석하고 수정  
  - 안전하지 않은 코딩 방식이 런타임 오류 및 보안 취약점으로 이어질 수 있음을 확인  
  - HMAC을 이용하여 메시지 인증 코드 생성 및 메시지 무결성 검증 과정 확인  
  - 동일 입력과 동일 키 사용 시 동일한 HMAC 값이 생성되는 특성 확인  
  - AES-ECB 모드로 평문을 암호화하고 반복되는 평문 블록이 암호문에서도 동일하게 나타나는 취약점 확인  
  - 이미지 파일을 ECB 방식으로 암호화하여 암호화 이후에도 원본 구조가 식별 가능한 문제 확인  
  - 반복 문자열 데이터를 소켓 통신으로 전송하고 ECB 암호문에서 동일한 패턴이 반복되는 현상을 Wireshark로 관찰  
  - AES-CTR 모드로 동일 데이터를 암호화하여 ECB와 달리 패턴이 나타나지 않는 특성 확인  
  - CTR 모드가 nonce 및 counter 기반으로 동작하여 동일 평문이라도 다른 암호문이 생성되는 과정 확인  
  - AES-GCM을 이용하여 평문, 키, Nonce, AAD, Ciphertext, Tag 구성 요소 및 암호화/복호화 과정 확인  
  - AES-GCM이 AEAD 방식으로 기밀성과 무결성을 동시에 제공함을 확인  
  - AES-GCM 기반 소켓 통신을 구현하여 노드 간 암호화된 메시지 송수신 실습 수행  
  - 인증 태그(Tag)를 이용하여 데이터 위변조 여부를 검증하는 과정 확인  
  - 평문 통신과 AES-GCM 적용 통신을 비교하여 Wireshark에서 평문은 쉽게 분석되지만 암호화 데이터는 식별이 어려움을 확인  
  - ECB, CTR, GCM 모드 간 보안 특성을 비교하여 암호 모드 선택이 보안에 미치는 영향 이해  
  - 보안 통신은 단순 암호화가 아닌 무결성 검증과 인증까지 포함해야 안전함을 확인

  #### **AUTOSAR OVERVIEW**  
  **1. 소프트웨어 플랫폼**  
  - 소프트웨어 플랫폼 개요 : 제어계층에서 응용 SW와 HW를 연결해주는 중간 계층으로, 표준 인터페이스와 공통 기능 모듈을 제공함
  - 소프트웨어 플랫폼 개발 배경 : 제어기 수량의 증가 및 차량 공간의 제약에 따라 제어기 통합이 필요하며, 제어기 SW의 복잡성이 증가함에 따라 플랫폼 공용화 및 표준화가 필요하기 때문
  - HKMC 표준 플랫폼 비교 (XENON AUTOSAR) : 최신 차량용 기반 기술의 국제 표준화 및 사양화, 고성능 MCU 사용으로 플랫폼 적용 도메인 확대 및 전 분야 공용 표준화 플랫폼 제공

  **2. AUTOSAR 란?**
  - AUTOSAR 정의 : AUTOmotive Open System ARchitecture, 더욱 향상된 성능과 안전성 및 친환경적인 전장 시스템의 혁신을 위한 기반을 조성하기 위해 자동차 수명 전반에 걸쳐 소프트웨어와 하드웨어의 교체나 업데이트를 가능하게 함
  - AUTOSAR 운영조직 : 참여 정도에 따라 4개의 조직으로 구성됨
    - Core Partner - 조직 및 행정 관리
    - Premium Partner - Working group의 선도 및 개선
    - Development Partner - 전문 지식 기여
    - Associate Partner - AUTOSAR 표준 사용자
    | 항목 | Classic AUTOSAR | Adaptive AUTOSAR |
    |-----|-----------------|------------------|
    | 대상 하드웨어 | MCU | MPU |
    | 운영체제 | OSEK/VDX 기반 RTOS | POSIX 기반 OS |
    | 프로그래밍 언어 | C | C++, 일부 Python |
    | 통신 방식 | 정적 통신 구성 | 동적 서비스 기반 통신 |
    | 적용 분야 | 샤시, 파워트레인, 진단 | IVI, 쟈율주행, V2X 등 |
    | 구성 방식 | 정적 구성 | 동적 구성 |
    | 주요 특징 | 실시간 경량, 고신뢰성 | 고성능 처리, 유연성, OTA |
    | RTE 사용 여부 | 사용 | 미사용 |

  **3. AUTOSAR 플랫폼**
  - AUTOSAR 개발 과정
    1. Configure System : 시스템 설정 단계로 컴포넌트의 구성/연결 등을 정의
    2. Implement Component : "Configure System" 단계에서 구성한 컴포넌트들에 대한 코드 구현 등을 진행
    3. Extract ECU-Specific Information : 시스템 구성 정보로부터 특정 제어기 소프트웨어를 구현하기 위한 정보만을 추출
    4. Configure ECU : 제어기 관련 설정을 진행 (ECU Configuration Description 개발)
    5. Generate Executable : 제어기에서 동작하는 실행 파일을 생성
    - 차량 시스템은 신뢰성이 중요하기 때문에 사람이 직접 코딩하는 것을 막으려고 함
    - AUTOSAR 개발 과정은 일반적으로 Top-Down 방식 
    - 시스템 설계자는 VFB 상에서 SW-C를 설계. SW-C 간 Data의 이동은 Port와 Interface로 정의
    - Configure System이라는 디자인 단계에서 SW-C는 특정 ECU에 할당. ECU Extract 과정을 통해 개별 ECU에 설계 정보 전달
    - 개별 ECU는 SW-C 간 또는 SW-C와 BSW간 구체적인 인터페이스를 RTE를 통해 구현
    - SW-C : Software Component, 일반적으로 소프트웨어 기능 단위를 의미
    - VFB : Virtual Functional Bus, 컴포넌트가 상호작용 할 수 있는 통신 메커니즘
    - RTE : Run-Time Environment, SW-C 간 또는 SW-C와 BSW간 인터페이스 설정을 통해 자동 생성해주는 기능
  
  - AUTOSAR 플랫폼 구조
    - 차량용 SW Application 개발의 생산성 향상을 위한 표준 플랫폼으로 계층화된 구조를 사용해 업체별 개발 분담이 가능 (Application, BSW, MCAL), AUTOSAR 표준 준수를 통한 안전성 확보 및 H/W와 독립적인 구조를 통해 SW Application 재사용 가능
    - AUTOSAR Layered Software Architecture
      - Application Layer - H/W 독립적인 응용 프로그램 S/W를 정의
      - Runtime Environment (RTE) - VFB로 모델화된 통신 구조가 실제 로컬 연결이나 네트워크 통신으로 구현된 환경
      - AUTOSAR Inferface - 사용자 설정에 따라 생성되는 API
      - Standardized AUTOSAR Interface - AUTOSAR Interface와 동일한 API 구조를 갖지만 표준에 정의된 Interface를 사용
      - Standardized Interface - 표준 Interface와 BSW간 Data를 주고 받거나 동작을 실행하기 위한 API
      - Basic Software Layers (BSW)
        1. Services Layer - 시스템 구동 및 다른 BSW 모듈 제어를 위한 관리 서비스 제공
        2. ECU Abstraction - MCAL 드라이버들을 상위 계층에 Interface하는 추상화 계층
        3. Micro-Controller Abstraction Layer - MCU 내부 장치를 이용하기 위한 드라이버들로 구성
        4. Complex Drivers - AUTOSAR 표준에 정의되지 않은 기능 구현을 위한 계층
  
  **4. What are the benefits?**
  - SW Reusability : SW 플랫폼을 통한 HW 독립적인 SW 애플리케이션 설계 및 재사용 
  - SW Safety : 안전이 검증된 S/W의 재사용이 가능해 안전성이 확보됨
  - Cost efficiency : S/W 재사용 및 신차 모델 개발 기간 단축으로 인한 원가 절감, 부품사와 명확한 커뮤니케이션 가능, 다양한 OEM에 공급 가능
